## Observations

**Regression vs. the prior 20/20 run (old 5-10 prompt, old 20-task narrative set):**
count_ok dropped from 20/20 (100%) to 20/21 (95.2%). The ONE failure is task 4,
"Start going to gym" (bucket: health, a CONCRETE task, not one of the 3 vague ones) -
it produced 10 steps against the new 5-8 cap. This is a real, small regression caused
by tightening the range from 5-10 to 5-8: the model's natural output length for this
input didn't shrink to match the new tighter ceiling. format_ok held at 100% (21/21,
up from 20/20) so output shape is still fully clean. Latency actually IMPROVED
across the board (p50 8.63s vs 11.62s before, p95 12.86s vs 19.71s, max 18.07s vs
26.58s) - consistent with the new terser imperative-phrase inputs needing less
prefill and the model, prompted for 5-8 rather than 5-10, generating somewhat less
text on average.

**Vague vs. concrete - the vague inputs did NOT perform worse on the metrics that
matter for the bar** (count_ok 3/3, format_ok 3/3, avg 8.0 steps vs 8.11 for
concrete - i.e. no thinner output, no retries structurally possible since this is
single-shot generation and none were needed to hit 5-8/clean format). However there
is a real, measurable difference worth flagging: vague inputs were about 44% slower
(avg 12.93s vs 8.96s for concrete), driven by the model generating longer, more
verbose step text per bullet (e.g. "Get motivated" hit the run's single highest
latency, 18.07s, with steps quoting long self-referential phrases). Qualitatively,
the vague outputs are also noticeably more generic/ungrounded than the concrete
ones - "Be better" produced business-consulting-flavored steps ("Review client's
goals and objectives", "Establish accountability and tracking system", "Set up a
budget and resources") that read like a corporate coaching template rather than
personal advice, because there is no content in "Be better" to ground a
personalized breakdown in. This is a real quality gap on the 3 vague tasks even
though it does not fail the formal bar.

**Category spot-check (categorize() second call) - this is the weakest number in
this run: only 55.6% (10/18) on the concrete tasks.** Failure pattern: a strong
bias toward guessing "work" whenever the input is not obviously about a job -
"Start going to gym", "Fix my sleep schedule" (health), "Study for exam", "Read
more books" (learning), "Create a budget", "Start investing" (finance), and
"Reduce screen time" (personal) were ALL misclassified as "work". "Pay off debt"
produced a non-taxonomy word ("debt") that fell through to the DEFAULT_CATEGORY
fallback ("personal") rather than "finance". Two of the three vague tasks also
guessed "work" ("Be better", "Get motivated"), consistent with this same bias, and
"Fix my life" guessed "personal". This is NOT scored against the PASS/REVIEW bar
(which is step-count/format only) but it is a real, not-rounded-up problem: the
categorize() call as currently prompted is not reliable enough to ship as-is for
filtering/grouping features - it needs either a few-shot example per category in
CATEGORIZE_SYSTEM_PROMPT, or a lower temperature / greedy decode for this specific
call (currently shares GEN's temperature=0.3, top_p=0.9 - worth trying
temperature=0 since this is single-token classification, not creative generation).

**Failure modes seen:** one count_ok miss (task 4, over cap at 10 steps, see
above). Zero refusals, zero empty-results, zero runtime errors across all 21
generation calls and all 21 categorize calls. Task 4's raw output used a nested
`\t*` sub-bullet under step 3 ("Pack gym bag with:") which the parser still
counted as separate top-level steps (Water bottle / Towel / Gym shoes / Any other
essentials) - this is the direct cause of the 10-count overage, worth noting as a
prompt-wording risk (the current wording does not discourage the model from
itemizing a packing list as sub-steps).

**Prompt/decoding tweaks tried:** none in this run - straight re-eval of the v2
prompt against the SAME deployed .pte (HF software-mansion/react-native-executorch-
llama-3.2, revision v0.4.0, llama-3.2-1B/QLoRA/llama3_2_qat_lora.pte). GEN
unchanged: temperature=0.3, top_p=0.9, max_new_tokens=256. Byte-identity of SYSTEM
between OverwhelmService.ts, ml/test/overwhelm_eval.py, and this kernel's SYSTEM was
verified character-for-character before this run (227 chars, exact match) - the
eval reflects the real shipping prompt.

**Device measured on (for latency):** a cloud-notebook CPU (GPU disabled -
irrelevant anyway, .pte is XNNPACK/CPU-delegated). NOT a Snapdragon device. No
on-device ARM measurement has been taken yet - still the top open item before
quoting a demo-facing latency number.
